title: Clousight Bench
description: Run recognized benchmarks reproducibly against managed cloud products and LLMs — one command, a provenance-checked number.
---

**Clousight Bench** runs recognized benchmarks — SWE-bench, TPC-DS/H, YCSB, TPC-C,
MMLU, GSM8K, HumanEval — **unmodified** against managed cloud products and LLM
endpoints, and gives you a number with a verifiable provenance chain: which
benchmark, which pinned dataset, which evaluator, on which system-under-test.

It never re-scores a benchmark or blends scores. The benchmark's own harness
produces the verdict; the framework adds the reproducibility bookkeeping and the
cloud-product dimensions (latency, cost, per-item scores, an optional LLM judge).

## Quickstart

<Steps>
<Step title="Install">
```bash
pip install clousight-bench          # extras as needed: [store] [llm] [tpcds] [swebench]
# or, from a clone:  uv sync --all-extras
```
</Step>
<Step title="See what's installed">
```bash
csbench list
```
Every registered benchmark, evaluator, and platform — plus a copy-pasteable
"run one" hint.
</Step>
<Step title="Run one — offline, no cloud, no key">
```bash
printf 'target:\n  mode: mock\n' > mock.yaml
csbench run --domain agent-runtime --benchmark swe-bench --platform local-sim --config mock.yaml
```
You get a `status: completed` record on stdout. ✅ That's a full run of the stage
machine (resolve → prepare → run → score → persist) over a bundled fixture — no
cloud account, no API key.
</Step>
<Step title="Point it at a real system (config-connect)">
```bash
printf 'target:\n  mode: runtime\n  endpoint: "https://dashscope.aliyuncs.com/compatible-mode/v1"\n  model: qwen-max\n  credentials_ref: env:DASHSCOPE_API_KEY\n' > qwen.yaml
export DASHSCOPE_API_KEY=...
csbench run --domain llm --benchmark mmlu --platform llm-endpoint --config qwen.yaml
```
Same command shape; now the number comes from a live endpoint you already run.
Then `csbench serve` opens the web viewer at `http://127.0.0.1:8787`.
</Step>
</Steps>

<Tip>
Gate a benchmark in CI with a threshold: `csbench run … --assert thresholds.yaml`
exits non-zero if any measurement misses its bound. See [pytest & CI](/docs/pytest-ci).
</Tip>

## The mental model

Three things, each a plugin discovered by an entry point:

- A **`BenchmarkSuite`** wraps a recognized harness (or any reproducible workload):
  `resolve → prepare → run → mock_artifacts`.
- An **`Evaluator`** turns the run's artifacts into namespaced **`Measurement`s**
  (and optional per-item **`items`**) — a pure, offline, re-scorable function.
- The **system under test** is chosen by `--platform` + a `target`: a simulated
  reference, an **already-running service you config-connect to** (endpoint +
  credentials), or a cloud the framework provisions.

You add a benchmark by writing a Suite + Evaluator; you run it with
`csbench run --benchmark <id>`. See [Add a benchmark](/docs/adding-a-suite).

## The reproducibility contract

Every record carries a `provenance` block (benchmark id, pinned dataset digest,
evaluator id, `unmodified` flag, scaffold) plus three independent fingerprints
(`benchmark` / `environment` / `implementation`), so you can tell whether two
numbers are even comparable. Every measurement carries a `reproducibility_class`:

| Class | Meaning |
|---|---|
| **deterministic** | Same inputs, same number — e.g. `swe-bench.resolved`, `mmlu.accuracy` |
| **environmental** | Method reproducible; the number drifts with network/region/account — cost, latency |
| **judge-based** | An LLM-as-judge is in the loop — see [Judges](/docs/judges) |

`official=true` measurements are the benchmark's own verdict under its
`<suite_id>.` namespace (a provenance flag, enforced by `csbench conformance`);
add-on [metrics](/docs/metrics) and community evaluators stay in their own space.
Results are always **per dimension — never a blended score**.
